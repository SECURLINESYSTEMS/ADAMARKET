# CRM SaaS — решение по окружению и доступу к заявкам

Дата: 15 октября 2026  
Статус: проектное решение; никакие изменения Supabase не применялись.

## Принятые требования

- Предпочтение пользователя: использовать существующую инфраструктуру проекта ADAMARKET, но не изменять production без отдельного согласования.
- Сотрудник видит только заявки, назначенные ему.
- Владелец и администратор могут видеть все заявки только внутри своей организации.
- Новая CRM не должна использовать таблицы ADAMARKET как хранилище данных CRM и не должна менять существующую авторизацию маркетплейса.
- Telegram-бот и Telegram-функции ADAMARKET не включать в новый продукт.

## Важное ограничение окружения

«Тот же Supabase project» не означает, что можно безопасно выполнять DDL в production. Проект содержит существующую рабочую схему и авторизацию. Поэтому первый технический этап — только чтение метаданных и подготовка миграций в GitHub.

Перед выполнением любой SQL-миграции необходимо создать изолированную development branch Supabase (если функция доступна и пользователь подтвердил стоимость) либо использовать отдельный тестовый Supabase project. Development branch имеет собственную базу и project ref; production data не переносится. Не создавать ветку автоматически, пока не известна и не подтверждена стоимость.

Нельзя считать создание отдельной схемы внутри production полноценной изоляцией: миграция всё равно меняет production, а настройки exposed schemas, RLS и grants требуют осторожной проверки.

## Доступ к заявкам

Предлагаемая логика:
- Owner: читать все заявки своей организации; управлять участниками и настройками.
- Admin: читать все заявки своей организации; создавать и назначать заявки; управлять задачами и статусами в пределах разрешений.
- Member: читать только заявки, где `assigned_to = auth.uid()`, и только если он состоит в организации этой записи.
- Member может менять только разрешённые поля назначенной ему заявки (например, статус, комментарий/результат, фактическое время); не может менять `organization_id`, назначать себя на чужую заявку или менять роль.
- По умолчанию Member не может удалять заявки, менять ответственного или просматривать полные списки клиентов, если клиентские записи не связаны с его назначенными работами. Эти права требуют явного решения.
- Задачи доступны Member только если они назначены ему и принадлежат заявке/организации, к которой у него есть доступ.
- Журнал действий доступен только в пределах прав на связанную сущность; административные события — Owner/Admin.

## Проектная схема доступа

Бизнес-таблицы должны содержать `organization_id`. В таблице заявок требуется `assigned_to` (UUID пользователя, nullable только для неназначенных заявок). RLS проверяет одновременно:
1. запись принадлежит организации;
2. пользователь — активный участник этой организации;
3. роль пользователя соответствует операции;
4. для Member запись назначена именно ему.

Не полагаться на скрытие кнопок в интерфейсе. Все ограничения должны обеспечиваться RLS и при необходимости безопасными серверными функциями. Проверять SELECT, INSERT, UPDATE и DELETE отдельно.

## Обязательные тесты перед пилотом

1. Member A видит назначенную ему заявку в организации A.
2. Member A не видит заявку организации A, назначенную Member B.
3. Member A не видит заявку организации B даже при известном UUID.
4. Member A не может вставить заявку с чужим organization_id.
5. Member A не может переприсвоить себе чужую заявку через UPDATE.
6. Member A не может изменить назначение или organization_id.
7. Owner/Admin организации A видят все заявки A, но не заявки B.
8. Пользователь без членства и отключённый участник не имеют доступа.
9. Задачи, клиенты и журнал не раскрывают данные через обходные связи.
10. Проверки выполняются только в development branch / тестовом проекте.

## Следующий шаг

1. Уточнить возможность и стоимость Supabase development branch.
2. Только после явного подтверждения затрат создать изолированную ветку.
3. На ветке проверить конфигурацию схем, миграций и API exposure.
4. Подготовить первую SQL-миграцию для новых таблиц CRM SaaS, с префиксом/пространством имён, без изменения существующих таблиц.
5. Написать тесты RLS на две организации и три роли.
6. Не объединять и не деплоить миграции в production без отдельного согласования.
